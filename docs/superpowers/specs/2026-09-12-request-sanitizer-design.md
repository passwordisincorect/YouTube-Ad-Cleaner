# YouTube Ad Cleaner v1.3.0 Request Sanitizer Design

## Goal

Prevent YouTube web player sessions from entering an ad state by sanitizing supported player request bodies before they are sent, while retaining the v1.2.x response sanitizer as a secondary layer and preserving fail-open playback behavior.

## Evidence and scope

The user's Stats for nerds showed `SABR` without `SSAP`, so this design targets standard YouTube web player requests rather than server-side ad insertion. Current uBlock Origin quick fixes also operate on `/player` request bodies as well as player responses, but some stronger client impersonation variants have caused breakage. v1.3.0 therefore uses a conservative request mutation rather than broad client spoofing.

## Architecture

`page-hook.js` remains the MAIN-world script loaded at `document_start`.

Before network dispatch:

1. Detect supported player endpoints: `/youtubei/v1/player`, `/youtubei/v1/get_watch`, and `/youtubei/v1/playlist/watch`.
2. Parse JSON request bodies only when safely possible.
3. If `playbackContext.contentPlaybackContext` exists, set `isInlinePlaybackNoAd = true`.
4. Remove clearly ad-specific request context such as `adSignalsInfo` when present.
5. Preserve authentication, visitor data, video ID, playlist data, captions, attestation, age/content checks, client name/version and all unrelated fields.
6. Serialize the modified body and send it through the original Fetch/XHR implementation.
7. If parsing or mutation fails, send the original request unchanged.

After response receipt, keep the existing player-response sanitization for `adPlacements`, `playerAds`, `adSlots` and known nested ad renderers.

## Fetch handling

The Fetch wrapper sanitizes the outbound body before calling the original `fetch`, then sanitizes the returned player JSON response. It supports:

- `fetch(url, { body: JSON string })`
- `fetch(Request, init)` when a body is explicitly available in `init`

It does not consume opaque/request streams that cannot be reconstructed safely; those requests fail open.

## XHR handling

`XMLHttpRequest.open()` records the resolved URL. `XMLHttpRequest.send(body)` sanitizes the outbound JSON string when the URL is a supported player endpoint, then calls the original `send` with the sanitized body. Existing response interception remains intact for text/default and JSON responses.

## Cold loads

Cold watch-page loads can contain `ytInitialPlayerResponse` generated by the server before browser-side request hooks run. v1.3.0 continues to sanitize that object in place rather than deleting it or forcing a reload. This avoids known breakage with livestreams and avoids deliberately creating a second player request.

## Safety constraints

- No Skip Ad click.
- No mute.
- No seek/currentTime modification.
- No playback-rate modification.
- Do not block `googlevideo.com`.
- Do not block YouTube player endpoints with DNR.
- Do not spoof `clientName`, `clientVersion`, `clientScreen`, visitor IDs, auth tokens, attestation or content-check fields.
- Request and response sanitizers are fail-open.
- Turning the extension off must stop both request and response sanitization.

## Testing

Add regression tests for:

- player URL recognition including get_watch and playlist/watch;
- request sanitizer preserving unrelated player data;
- `isInlinePlaybackNoAd` insertion;
- removal of `adSignalsInfo`;
- malformed request body fail-open;
- Fetch outbound body mutation before original fetch is called;
- XHR outbound body mutation before original send is called;
- non-player requests unchanged;
- toggle disables outbound mutation;
- all existing response, DOM, manifest, DNR and release-note tests remain green.
